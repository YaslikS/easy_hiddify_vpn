# Правила работы с проектом

## 1. Язык общения

- Всегда общаться с пользователем, писать пояснения, отчёты и комментарии только на русском языке.

## 2. Точечное чтение и проверка изменений

- Читать только те участки файлов, которые относятся к задаче. Не выгружать в контекст огромные логи, дампы или сгенерированные файлы: lock-файлы, build-директории, `.git`, `venv`, `.gradle`.
- Никогда не запускать `find`, `tree`, `ls -R` или рекурсивный `grep` по всему репозиторию без крайней необходимости.
- Если в запросе не указаны пути к файлам, сначала запросить их у пользователя или изучить только структуру корневого каталога (`ls -la`).
- Никогда не запускать полную сборку (`./gradlew build` или `assembleRelease`) для проверки мелких правок: это долго и расходует лимиты.
- Для проверки компиляции использовать быстрые таргеты: `./gradlew compileDebugKotlin`. Для точечной проверки тестов использовать `./gradlew testDebugUnitTest --tests "com.example.TargetTest"`.

## 3. Безопасность и границы рабочей области

- Категорически запрещается просматривать, читать, искать или изменять файлы и папки за пределами корневой директории текущего проекта без предварительного явного разрешения пользователя.
- Не выполнять неочевидных или выходящих за рамки прямого запроса действий без уточнения у пользователя.
- Категорически запрещается добавлять хардкод локализации, включая выдуманные языковые ключи и поля вроде `*_kk`, `*_kz` и подобных, которых нет в серверных DTO, а также обращаться к полям, отсутствующим в DTO или контрактах API, без прямого указания пользователя.

## 4. Код-стайл и правила вёрстки компонентов

### Форматирование и именованные аргументы в Kotlin

- Если в объявлении или вызове функции, конструктора или класса больше одного параметра или поля, всегда писать их в столбик: каждый параметр или поле на новой строке.
- При вызове функций и конструкторов в Kotlin всегда использовать именованные параметры (`paramName = value`).

### Запрет на лишние одноразовые переменные и перекладывание констант

- Категорически запрещается создавать локальные переменные, которые используются только один раз отдельно от вёрстки, например: `val isNameError = ...`, `val isSaveEnabled = ...`, `val isSelected = ...`, `val showCustomField = ...`, `val borderColor = ...`, `val height = 50.dp`, `val shape = Rounded8`.
- Все одноразовые выражения, флаги и вычисления, включая обёрнутые в `remember(...)`, необходимо подставлять напрямую в параметры UI-компонентов на месте их вызова.

### Строковые ресурсы вместо хардкода

- Все дефолтные пользовательские тексты и подсказки в компонентах брать из строковых ресурсов (`res/values/strings.xml` и `res/values-ru/strings.xml`), а не хардкодить строковыми литералами.
- Например, для `BaseSearchBar` использовать `placeholder: String = stringResource(R.string.search)`.

### Геттеры `*NotNull` в DTO и стабильность ключей Compose

- Во все DTO и модели данных добавлять геттеры с суффиксом `NotNull`, возвращающие non-nullable значение по умолчанию, например: `val emailNotNull: String get() = email ?: ""`, `val idNotNull: Int get() = id ?: 0`. В UI-слое использовать именно эти геттеры.
- В ключи `remember(...)` передавать конкретные стабильные поля: примитивы, строки, enum — через `*NotNull`, а не весь объект целиком. Например: `remember(user.emailNotNull, user.phoneNotNull) { user.emailNotNull.isEmpty() && user.phoneNotNull.isNotEmpty() }`.
- Вычисляемые в теле `@Composable` значения (выбор ресурса иконки через `when`, булевы флаги, формирование объектов) и переиспользуемые лямбды-обработчики (например, `handleCloseAttempt`) обязательно оборачивать в `remember(...)` с соответствующими ключами или в `derivedStateOf`, чтобы они не пересчитывались и не пересоздавались на каждую рекомпозицию.
- Никогда не объявлять голые вычисляемые переменные и лямбды (`val handleCloseAttempt = { ... }`) напрямую в теле `@Composable`.

### Отказ от устаревших методов и классов

- По возможности не использовать методы, конструкторы и классы с `@Deprecated` из стандартных библиотек Java/Kotlin/Android SDK, сторонних зависимостей и самого проекта. Всегда выбирать актуальные рекомендуемые альтернативы.

### Стабильные коллекции в UI-слое

- При передаче списков и коллекций в UI-состояния (`State`) и параметры `@Composable`-функций предпочитать неизменяемые коллекции из `kotlinx.collections.immutable`: `ImmutableList`, `PersistentList`, `ImmutableSet`, `ImmutableMap`.
- Создавать такие коллекции через `persistentListOf(...)`, `.toImmutableList()`, `.toPersistentList()` и аналогичные API.
- Стандартные `List`, `Set` и `Map` не являются стабильными типами для компилятора Compose и приводят к лишним рекомпозициям.

## 5. Git

- Заголовок и описание коммита всегда писать на английском языке.
- Начинать заголовок с префикса по типу изменения:
  - `- feature:` — новая функциональность.
  - `- fixed:` — исправление ошибки.
  - `- docs:` — документация.
  - `- proj:` — настройки проекта и сборки, например Gradle.
  - `- git:` — изменения, относящиеся к Git.
